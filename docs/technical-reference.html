1Overview#

MUTAV is an institutional fiador for Brazilian rental leases. The mutav program holds a BRL reserve in BRS (a BRL token issued by Nora) and records every guarantee MUTAV gives, with its remaining cover. It mints reserve shares to allowlisted capital providers at an on-chain NAV, and it gates new guarantees and redemption fills on required coverage against the registered cover. The coverage gate never applies to a claim payment: within admin-set caps, a claim payment always goes through. The program keeps internal accounting, so tokens sent to it do not move NAV. It prices nothing, decides no claim and holds no personal data: those duties stay in the MUTAV platform, which acts on-chain through the operator key.

Architecture in one line. Reserve admin (Squads multisig), operator key, pauser and guardians sign instructions to mutav; one VaultConfig per reserve mint; a vault authority PDA owns every reserve token account and the share mint; clients compose unsigned transactions through @mutav-finance/mutav-protocol-solana.

The reserve is operational infrastructure that backs the guarantees, not a yield product. During the pilot the reserve is not open to public investment.

The claim window is 31 daily buckets: a payment goes through only if the payments of the last 31 days plus this one stay within max_claim_per_period, so no 30-day span pays more than the cap. Its length is fixed by the bucket count, not by a parameter. There is no take on issuer income in v1: the field was removed and returns as a carve if a take is ever decided (spec §12 Q47).

The devnet NAV-move bound is 100% on purpose: on a small demo reserve a single claim is a real NAV move and would halt fills. The guard is proven in LiteSVM tests and is lowered for the real pilot; that value is not decided yet. Every other value above is set by ADR 0028 for the pilot too.

Why these values (ADR 0028). c = 0.25 holds a quarter of every lease's remaining cover, two and a half times the program floor, because the first real book is small and its loss data is not ours yet. max_tvl (R$1M) is the ceiling of a capital plan that arrives with the book, not a target. The operator pays claims without the multisig up to R$15k per call and R$20k per 31 days: a 6×-rent eviction (R$13,200 at a R$2,200 rent) fits the per-call cap, and the bounded loss from a compromised operator key stays R$20k per 31 days, about 2% of max_tvl. R$120k per guarantee fits the working product (R$39,600: 12× + 6× a R$2,200 rent) with room. At c = 0.25 each such lease needs R$9,900 of required coverage. Raising any cap is a time-locked multisig action.

5Instructions#

Common rules. An account whose version is above 1, or whose status, leg, kind or mode byte is unknown, is refused with UnsupportedVersion. Every BRS transfer uses transfer_checked with the stored reserve mint and token program. A debit from a capital provider requires the token account's owner to be the signer; delegates are never used. Every program account is checked by seeds and canonical bump; token accounts by mint, owner and token program. Math is u128, checked, rounded in the reserve's favour (MathOverflow on overflow). 6Economics & math#

All amounts are BRS base units; BRS is valued at par with BRL. Products use u128 and narrow back to u64, failing with MathOverflow instead of truncating. The core primitive is mul_div(a, b, d, rounding). Rounding is always in the reserve's favour: down for what it pays or mints, up for what it requires or is owed. Inputs are tracked balances only. The code lives in programs/mutav/src/math.rs and coverage.rs, mirrored in the client's math.ts.

6.1 Coverage quantities#

stable_assets         = brs_balance + adapter_value        // tracked only; frozen reserve = 0; adapter_value = 0 in v1
                                                           // computed at every gate, never cached
remaining_cover(g)    = (default_cover − default_paid) + (exit_cover − exit_paid)
remaining_cover_total = Σ remaining_cover(g) over guarantees not CLOSED
unprovisioned_cover   = max(0, remaining_cover_total − provisions)

coverage_required     = max( ceil(coverage_ratio_bps × remaining_cover_total / 10,000),
                             provisions + min(stress_buffer, unprovisioned_cover) )

surplus               = max(0, stable_assets − coverage_required)
free_capital          = surplus
liquid_budget         = max(0, brs_balance − provisions)
net_assets            = max(0, stable_assets − provisions)
mode                  = UNDER_COVERED if stable_assets < coverage_required, else NORMAL
underwater            = shares_outstanding > 0 and net_assets × 10^9 < shares_outstanding
  • coverage_required ≥ provisions always: filed claims are held in full. A provision lowers NAV (through net_assets), never stable_assets.
  • One helper (coverage::coverage_required) computes it for every gate and every cached recompute. The stress term saturates. On the claim path (file_claim, pay_claim, close_guarantee) the cached write saturates too (u64::MAX on overflow), so those instructions never fail on it; register_guarantee and set_config compute it checked and fail closed.
  • stress_buffer ≤ max_tvl; 0 turns the stress term off. set_config recomputes the cache after any change.

Stress buffer. Claims arrive per event: one month's rent per default claim, one exit payment at the end of the occupation. The stress buffer is the R$ amount of the claims that could be filed next, not every full cover. The admin sizes it from the portfolio (for example the three largest rents plus one exit payment). Devnet and pilot: R$19,000, set and locked. It gates new guarantees and redemption fills; it never gates a claim payment.

Illustrative example (not devnet data), with c = 0.25 and stress_buffer = R$19,000:

6.3 NAV and share pricing#

V                  = 1                                                   // virtual offset 10^0
shares_for(assets) = floor(assets × (shares_outstanding + V) / (net_assets + 1))
assets_for(shares) = floor(shares × (net_assets + 1) / (shares_outstanding + V))
conversion_nav     = floor((net_assets + 1) × 10^9 / (shares_outstanding + V))
published_nav      = 0                                                   if shares_outstanding = 0
                   = max(1, floor(net_assets × 10^9 / shares_outstanding))   otherwise
  • With V = 1 and a 6-decimal share mint, one share is worth 1 BRS at launch.
  • net_assets excludes pending deposits and claimable assets. Escrowed redeem shares stay in shares_outstanding until a fill burns them. shares_outstanding = minted supply + shares owed on filled, unclaimed deposits.
  • Every fill is priced at the NAV of that fill and rounds in the reserve's favour, so a fill never lowers NAV per share.
  • A deposit that would mint 0 shares, a redemption head worth 0 BRS, or a head whose price limit is not met stops the batch (RequestTooSmall, PriceLimitNotMet).
  • Inflows wait for the first shares. contribute_fees and sweep_income are refused with NoSharesOutstanding while shares_outstanding == 0, so no inflow can be lost to share rounding.
  • Underwater. NAV per share below the smallest published unit while shares are outstanding. An empty reserve is not underwater. Both fills refuse with ReserveUnderwater; cancels stay open; recovery is a MUTAV backstop (see §5.3).

6.4 Fee take and income intake#

guarantee fee:  take = floor(amount × fee_take_bps / 10,000)      → treasury_account
                net  = amount − take                              → reserve   (NAV rises, no shares)
issuer income:  amount                                            → reserve   (receipt kind ISSUER_STATEMENT)

Devnet and pilot fee_take_bps = 2,000 (20%); the program maximum is 3,000. There is no take on issuer income in v1. Issuer income is the issuer's partnership revenue, paid into the income inbox at an off-chain contractual rate; BRS itself bears no yield. Income is never a guarantee fee and never enters fees_in_total.

6.5 NAV-move guard and fill bounds#

at each inflow (contribute_fees, sweep_income):
    inflow_nav += ceil(net × 10^9 / shares_outstanding)              // saturating
guard_nav   = max(1, published_nav − inflow_nav)                     // 0 if no shares
halt if       |guard_nav − baseline| × 10,000 > max_nav_move_bps × baseline
              (only when baseline > 0 and guard_nav > 0)
  • Measured per share, so fills in the same window do not distort it.
  • Evaluated in refresh and inline once at the start of both fills. The inline check refuses with FulfilHalted but does not latch: a failed instruction cannot write state. The next refresh (anyone) latches fulfil_halted.
  • The halt is sticky. Only clear_fulfil_halt clears it, resetting the baseline to the current published NAV and inflow_nav to 0.
  • The baseline is seeded by the fulfil_deposits batch that mints the first shares, and cleared to 0 by the fulfil_redeems batch that burns the last ones, so a new first deposit is never compared with a NAV that belonged to old holders.
  • Fills and clear_fulfil_halt take nav_bounds { min, max }, composed when the proposal is created. A fill whose conversion_nav is outside the range is refused with NavOutOfBounds.

6.6 Claim bounds and the 31-day window#

unprovisioned(leg) = leg_cover − leg_paid − leg_provision

file_claim:   0 < amount ≤ unprovisioned(leg)
pay_claim:    expected_amount == filing.provision
              provision ≤ (leg_cover − leg_paid) − (leg_provision − provision)
              provision ≤ max_claim_per_call  or  approved_amount == provision
              Σ last 31 daily buckets + provision ≤ max_claim_per_period
              provision ≤ brs_balance, reserve not frozen

window:       day    = max(floor(now / 86,400), claim_day_anchor)
              clear every bucket more than 30 days before day
              window = Σ claim_day_buckets over the last 31 days, today included
              require  window + amount ≤ max_claim_per_period
              then     claim_day_buckets[day mod 31] += amount

The rule is exact: no weighting or estimate. Because every 30-day span lies inside some 31-day window of whole days, no 30-day span pays out more than the cap, approved payments included. A property test checks the rule across bucket reuse and a cap change mid-window. Devnet and pilot: R$15,000 per call, R$20,000 per 31-day window.

7Lifecycles#

7.1 Guarantee and claim#

  • Register (operator): coverage-gated, capped per guarantee. Cover counts in remaining_cover_total at once.
  • Close (operator): RELEASED or VOID; requires no open claim. Releases remaining cover. The account is never closed, so the public claims history stays readable.
  • File: the operator books the provision; NAV drops at once.
  • Pay: exactly the provision, to the payments account. Never refused for coverage, mode, pause or the NAV guard. Above max_claim_per_call it needs the later approve_claim; until then MUTAV pays bank-first.
  • Settle: the operator records the Pix end-to-end hash after MUTAV pays the agency.

7.2 Deposit and redemption queues#

  • Each request is its own PDA at a monotonically increasing seq. Seqs are never reused. Two requests sent at once may race on the seq; the client retries.
  • The admin fills in strict FIFO order at the NAV of the fill, inside its nav_bounds. Up to 8 per call.
  • Whole fills only in v1. A head larger than the budget waits until free capital grows. The consoles show what a stuck head needs against what is available.
  • Owners cancel or claim at any time, also under pause. The admin can cancel a pending request back to its owner. advance_queue_head clears dead seqs.
  • Entry is allowlisted. Exit is open to any holder, with the sub-minimum exit rule of §5.5.
  • MUTAV's capital wallet uses the same queues with no special treatment. During the pilot the reserve is not open to public investment.

9.1 Pause scope#

Pause never traps holders' money and never blocks a claim. The pauser and guardians pause with no time lock; the admin through its time lock. Only the admin unpauses.

9.2 Frozen reserve#

The issuer can freeze any BRS account. refresh emits ReserveFrozenDetected and counts a frozen reserve as 0 BRS; register_guarantee, both fills and clear_fulfil_halt refuse with ReserveFrozen. A freeze also blocks pay_claim; MUTAV then pays the agency by Pix from its own bank and the reserve reimburses the payments account after the freeze lifts. The reserve's money is split across separate token accounts so one freeze does not trap everything.

9.3 Underwater reserve#

Both fills refuse with ReserveUnderwater, so new money never pays for old losses. Cancels stay open. Until book_unsolicited(BACKSTOP) ships, the operator recapitalises with contribute_fees under a fresh invoice_ref_hash recorded as a backstop, sending needed / (1 − take). No shares are minted, so the money raises NAV for every holder. Claim payments continue within the caps throughout.

9.4 Operator-compromise runbook#

  1. Freeze. The pauser runs revoke_operator at once (it also clears the pending operator key), and pause if needed. If the pauser key is suspect, the admin runs revoke_pauser.
  2. Appoint. The admin proposes a new operator with propose_role(OPERATOR, key); the new key accepts with accept_role within 72 hours. A new pauser can be proposed in the same Squads proposal.
  3. Reconcile. The new operator compares the platform's contract registry and audit trail with on-chain events and refs_hash values since the compromise.
  4. Correct with ordinary operator actions. Fake registrations: close_guarantee(VOID). Until the later claim instructions ship, a fake filing stays provisioned and is never paid; later, amend_claim(0) withdraws it and reinstate_guarantee undoes a wrongful close. No admin rollback instruction exists.
  5. Accept the bounded loss. Claim payments made with the compromised key are irreversible, bounded by the caps, and landed in MUTAV's own payments account.
  6. Resume. The admin signs no redemption fill until reconciliation is done.

Pauser compromise. A stolen pauser key can stop claim payments by revoking the operator until a new operator accepts. The admin removes it with revoke_pauser and proposes a replacement; bank-first payment covers the gap. Admin key compromise. One member key cannot act alone: the multisig needs the threshold and the time lock, during which members can reject and the pauser can pause. Detection. The app shows an operator-activity feed (registrations, closes, filings and payments in the last 24 hours), and a monitor alerts when the owner of the payments account changes.

12Upgrade rules & layout freeze#

12.1 Two multisigs#

Authority is split across two Squads v4 multisigs with the same members: the admin multisig (5 minutes on devnet, 24 hours on a real-money pilot) and the upgrade multisig (1 hour on devnet, 7 days on a real-money pilot). Day-to-day admin work needs a short wait; replacing the program needs a long one, so holders can react. Both have no config authority; the time lock counts from approval; no multisig config change during an upgrade window. Pause and revoke_operator are not time-locked. The deploy scripts check the Squads v4 owner, the exact member set, the exact threshold and the time-lock floors, and refuse any cluster other than devnet by genesis hash.

12.2 Layout rules#

  • R1. First fields version (1) and bump. R1b. A version above the binary's, or an unknown status, is refused.
  • R2. Fixed-size types only; statuses are u8 constants; nested config structs end with their own _reserved: [u8; 32].
  • R3. Carved fields read zero as the safe default; flags are u8 or bits in a u64, never bool.
  • R4. _reserved is last, zeroed, never touched by logic; fields are carved from its front.
  • R5. Append-only: never reorder, retype or delete; a retired field becomes _deprecated_<name>; never rename an account struct.
  • R6. Update in place, so bytes written by a newer binary survive a rollback.
  • R7. Sizes pinned with a compile-time assertion per account. R8. Large accounts are boxed.

12.3 The layout freeze#

The first devnet deploy freezes layout v1. Before it, the grown padding, the removals of ADR 0019 and ADR 0026, the carves of §4.2, the new arguments (close_guarantee's reason, the nav_bounds of the fills and clear_fulfil_halt, Eligibility, pay_claim's expected_amount, the sparse set_config, advance_queue_head(queue, max)) and the new instructions, events and errors land together, and the golden fixtures (tests/fixtures/layout/v1/) are regenerated once more. After it, every change is a carve from padding or a new account, checked against the v1 fixtures. Layout tests cover golden layouts, v1 to v2 decoding, live fixtures, padding preservation, padding zero at init, the version guard, feature flags and reserved room for every planned carve.

12.5 Release workflow#

  1. Before merge. ADR and spec update in the same PR; new fields carved from _reserved; no diff in the pay_claim path; layout, padding-preservation, idl-compat, Codama and full LiteSVM suites green.
